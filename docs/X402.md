# The envelope on an x402 paid response

A buying agent pays for one call over x402 and gets back the paid body. This
page is about what happens before money moves on from an escrow hold: the
seller attaches the labeled-exchange envelope (docs/ENVELOPE.md) to the paid
response, and the buyer's agent runs the gate on it. Release happens only on
VERIFIED.

Reference code: `arcaeon.prove.x402_ext` (standard library only). It is a
reference with a **mock rail**: nothing is held, moved, refunded or settled
anywhere, and it calls no network.

## What x402 V2 says (sources)

Read on 2026-10-04 from the coinbase/x402 GitHub repository, branch `main`
(the spec notes the project's home as github.com/x402-foundation/x402):

- `specs/x402-specification-v2.md` (last changed in commit `dd927a26`,
  2026-04-21),
  https://github.com/coinbase/x402/blob/main/specs/x402-specification-v2.md
  - **5.1 PaymentRequired Schema** (5.1.1 JSON Payload, 5.1.2 Field
    Descriptions): the 402 answer, with `x402Version: 2`, `resource`,
    `accepts` and an optional `extensions` object. 5.1.2 defines the
    `Extensions` object: "a key-value map where each key is an extension
    identifier", each value `{"info": object, "schema": object}` (`info`:
    extension data from the server; `schema`: a JSON Schema for `info`), both
    required. Servers advertise extensions in `PaymentRequired` and clients
    echo them in `PaymentPayload`.
  - **5.2 PaymentPayload Schema**: the buyer's signed authorization, also
    with optional `extensions`.
  - **5.3 SettlementResponse Schema** (5.3.1 JSON Structure, 5.3.2 Field
    Descriptions): what comes back on the paid response: `success`,
    `errorReason`, `payer`, `transaction`, `network`, `amount`, and an
    optional `extensions` ("Protocol extensions data").
- `specs/transports-v2/http.md` (commit `aeef1bff`, 2026-03-05),
  https://github.com/coinbase/x402/blob/main/specs/transports-v2/http.md
  - **Payment Required Signaling**: HTTP 402 with a `PAYMENT-REQUIRED`
    header, base64 `PaymentRequired`.
  - **Payment Payload Transmission**: the `PAYMENT-SIGNATURE` header, base64
    `PaymentPayload`.
  - **Settlement Response Delivery**: the `PAYMENT-RESPONSE` header, base64
    `SettlementResponse`.
  - **Header Summary** and **Response Body**: all x402 data travels in those
    three headers; the body is the server's own business.
- `specs/transports-v2/mcp.md`, **Settlement Response Delivery**: the same
  object in `_meta["x402/payment-response"]` of the tool result.
- `specs/transports-v2/a2a.md`, **Settlement Response Delivery**: an array
  of `SettlementResponse` in the `x402.payment.receipts` metadata field.
- `specs/extensions/extension-offer-and-receipt.md` (commit `f2bbb5cb`,
  2026-03-12), the nearest existing extension: **5.1 Placement** puts a
  signed receipt in the `SettlementResponse` at
  `extensions["offer-receipt"].info.receipt`, and **2. Status, Evolution,
  and Forward Compatibility** says its "wire shape and field placement are
  not considered stable" and that unknown extension fields should be treated
  as unsupported. `specs/extensions/payment_identifier.md` shows the same
  `{info, schema}` shape under the key `payment-identifier`.

x402.org was fetched; the page is rendered by script and the fetch held no
spec text, so nothing here cites it.

The spec gives no registry or prefix rule for extension ids. Existing ids are
short kebab-case words (`offer-receipt`, `payment-identifier`, `bazaar`,
`sign-in-with-x`). That is the convention followed here.

## Where the envelope rides

On the **paid** response, inside the `SettlementResponse`, under one
extension id:

```text
SettlementResponse.extensions["labeled-exchange"].info.envelope
```

```json
{
 "success": true,
 "transaction": "0x1234...cdef",
 "network": "eip155:84532",
 "payer": "0x857b...6b66",
 "extensions": {
  "labeled-exchange": {
   "info": {
    "envelope": {
     "mediaType": "application/vnd.arcaeon.envelope.v1+json",
     "dsseEnvelope": {"payloadType": "application/vnd.in-toto+json",
                      "payload": "<base64 Statement>",
                      "signatures": [{"keyid": "did:key:z6Mk...", "sig": "<base64>"}]}
    }
   },
   "schema": {"$schema": "https://json-schema.org/draft/2020-12/schema", "...": "..."}
  }
 }
}
```

- The extension id is `labeled-exchange`, the name of the envelope's
  predicate (`https://arcaeon.io/labeled-exchange/v1`).
- The field under `info` is `envelope`. It holds the sidecar object exactly
  as `arcaeon envelope seal` wrote it; nothing is added or renamed.
- `schema` is a JSON Schema for `info`, as 5.1.2 requires. A reader does not
  trust it and does not check against it; `envelope verify` does the
  checking.
- Over HTTP the whole object is base64 in `PAYMENT-RESPONSE`
  (`x402_ext.encode_header` / `decode_header`). The paid body is the HTTP
  body; the envelope's subject digest names those bytes.

The envelope is sealed by the seller for the buyer: `audience` is the
buyer's own id, `deal` the exchange id both sides hold, `purpose` what the
body may be used for, `not_after` a short window.

## The buyer's check, then the release

```python
from arcaeon.prove import x402_ext as X

c = X.check(payment_response, body_bytes, "buyer-agent-7", "pay",
            signers=["did:key:z6Mk..."], deal="d-x402-1", record_dir="deals")
c.release          # what the escrow rule may do
c.decision         # the gate's decision: allow or refuse, and the word
```

`check` writes the body and the carried envelope to a throwaway directory
and calls `arcaeon.prove.gate.decide` with the action `pay` (or `act`).
There is no second verifier: `envelope verify` decides, the gate turns the
word into allow or refuse, and `check` turns that into `release`.

| verdict | gate on `pay` / `act` | `release` | what the buyer's agent does |
|---|---|---|---|
| VERIFIED | allow | true (when the settlement says `"success": true`) | the escrow rule may release |
| BROKEN | refuse | false | do not release; keep the evidence |
| COULD NOT LOOK | refuse | false | hold; read only, act on nothing |

- **BROKEN** (the body changed after sealing, a signature fails, another
  audience, deal or purpose, expired, a stray key): no release. With a deal
  id the gate writes its evidence pack (`DEAL-<deal>/gate/<stamp>/`: the body,
  the envelope, `evidence.json`), and `check` adds the settlement response as
  received, `x402-settlement-response.json`. `arcaeon gate packet` renders
  that pack for a dispute.
- **COULD NOT LOOK** (no `labeled-exchange` extension, an extension stripped
  in transit, an `info` without `envelope`, an unsigned envelope, no signer
  named, a response that is not one JSON object): the hold stays. Reading the
  body is allowed; nothing vouches for it. A stripped extension is never
  read as VERIFIED.
- Hostile input (not base64, not JSON, duplicate keys, deep nesting, wrong
  types, over 2 MiB) is an answer, never a traceback: COULD NOT LOOK or
  BROKEN, `release` false.
- `release` also needs `"success": true` in the settlement response. A
  VERIFIED body on a settlement that says it failed has nothing to release.

### The mock rail

`MockEscrowRail` is in memory and exists for tests and demos. `hold(deal,
amount, currency)` records a hold; `settle(deal, check)` moves it to
RELEASED only when `check.release` is true **and** the check was run with
that same deal id (a check without a deal id did not hold the envelope to
this exchange, so it could be a replay). A released hold is never released
twice. Anything else leaves it HELD and logs why; a BROKEN check also records
its evidence path. The rail never refunds: whether money goes back is the
human's decision, outside this code.

## What this does not prove

Everything in docs/ENVELOPE.md "What VERIFIED does not prove" holds here,
and in particular:

- **Not that the body is true, good or worth the price.** Release means the
  bytes are the bytes the named key sealed, for this buyer and deal, in date.
  A sealed answer can be wrong, and a sealed body can carry a prompt
  injection.
- **Not that the payment happened.** `success`, `transaction`, `payer` and
  `network` are read as the seller sent them. Nothing here checks a chain, a
  facilitator or a transaction hash.
- **Not who the seller is.** The did:key is whatever key the buyer chose to
  name (`signers`). Which key stands for which seller is the buyer's
  decision.
- **Not that the extension is standard.** `labeled-exchange` is not an
  x402 Foundation extension. A facilitator or client that does not know it
  will pass it through or drop it; a dropped one reads COULD NOT LOOK, so the
  hold stays.
- **Not once-only delivery across holds.** Inside one binding the same
  envelope can be presented twice. The mock rail releases a deal once; a
  real rail must keep its own record.

## Money stays in the human's loop

- No custody. This code holds no funds, keys to funds or balances. Holding
  other people's money is a licensing question for the owner and a lawyer.
- No real rail. There is no adapter to a chain, card network or
  facilitator. `MockEscrowRail` moves nothing.
- No refunds by itself. A refusal leaves the hold and the evidence for a
  person to decide on.
- No signing keys beyond the throwaway seeds the tests write to a temporary
  directory.
